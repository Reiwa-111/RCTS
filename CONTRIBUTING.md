# Правила разработки

1. Прочитай `docs/ROADMAP.md`, `docs/TESTING.md` и соответствующую спецификацию.
2. До изменения кода создай воспроизводимый тест проблемы.
3. Держи изменение небольшим: не совмещай рефакторинг, изменение формата и смену криптографических параметров в одном patch.
4. Не меняй формат v0.1 без отдельного ADR и новой спецификации.
5. Собери Release и Debug, запусти CTest; для изменений парсера используй sanitizers и fuzz regression corpus.
6. Обнови README/документы, если изменились CLI, ограничения, зависимости или поведение.
7. Не добавляй в репозиторий ключи, контейнеры с реальными данными, plaintext, build directories или пользовательские файлы.
8. В отчёте перечисли реальные команды и результаты. Не выдавай непроверенное за сделанное.
9. Для криптографических изменений обязательно укажи threat model, параметры, совместимость и независимое review.
10. Репозиторий ведётся локально. Коммиты допустимы для срезов состояния; push, публикация и теги — только по явному разрешению.

Предпочтение отдаётся простым решениям, которые можно проверить. Новая зависимость должна иметь конкретное обоснование.
