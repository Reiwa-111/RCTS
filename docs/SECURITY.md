# Security model and limitations


## Intended use

RCTS v0.1 is an experimental local file-encryption tool. Its intended security goal is confidentiality and integrity of file contents while the master key remains secret and the host environment is trustworthy. It is not a production-reviewed system and must not be the only protection for critical or irreplaceable data.

## Assumptions

- The master key is generated using the project's key generator and remains secret.
- The device, operating system, user session, compiler/build chain and OpenSSL are not compromised.
- The filesystem behaves within the assumptions of the implementation.
- The user keeps independent backups and can recover the key.

## Threats considered

An attacker may possess a container and its format/source, and may modify, truncate, append or rearrange bytes. The format authenticates records and metadata; parsing rules reject invalid structure. Knowledge of the algorithm or format is not treated as a secret.

## Security properties implemented by design

- 256-bit master-key material generated by OpenSSL CSPRNG.
- Per-container 256-bit key derivation with HKDF-SHA-256 and a random salt.
- AES-256-GCM encryption with a 128-bit authentication tag per record.
- Per-container nonce prefix plus record index.
- Header and record metadata authenticated as AAD.
- Authenticated record validation before plaintext is accepted.
- Exclusive temporary creation and no-clobber final publication.
- Bounded key-file reading and streaming file processing.

These are design properties, not a guarantee that implementation bugs are absent.

## Out of scope / not protected

- Malware, compromised OS, malicious administrator, memory inspection, process injection or physical access.
- Key loss or weak user handling of the generated key file.
- Metadata privacy: filenames, output paths, file sizes, timing and container presence are not hidden by this format.
- Secure deletion of the input, key file, temporary files, backups or all memory copies.
- Availability against disk exhaustion, malicious filesystem behavior or denial of service.
- Cryptographic misuse elsewhere in the application or dependencies.

## Key handling notes

The key is not a password and has no password-strengthening step. Do not place it in source control, command-line arguments, logs, chat messages or cloud-synced locations without understanding the exposure. Best-effort cleansing is not proof that all copies are erased. Losing the key means losing access to the encrypted data.

## File handling

RCTS aims to avoid replacing existing output files and publishes completed output only after processing and finalization. Temporary files may remain after abnormal termination. Directory synchronization is best-effort; the project does not claim universal crash durability across all filesystems.

Report suspected vulnerabilities privately to the maintainer before publishing exploit details. Include reproducible steps, affected revision and relevant environment; avoid attaching confidential files or keys.
