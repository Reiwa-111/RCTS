# Бинарный формат RCTS v0.1

**Версия формата в заголовке:** `1`  
**Все многобайтовые целые числа:** big-endian.  
**Размер заголовка:** 33 байта.

## 1. Заголовок

| Смещение | Размер | Поле | Описание |
|---:|---:|---|---|
| 0 | 8 | Magic | байты `52 43 54 53 0D 0A 1A 0A` (`RCTS\r\n\x1A\n`) |
| 8 | 1 | Version | `0x01` |
| 9 | 4 | Chunk size | `1 048 576` (`0x00100000`) |
| 13 | 16 | KDF salt | 16 случайных байтов от OpenSSL CSPRNG |
| 29 | 4 | Nonce prefix | 4 случайных байта от OpenSSL CSPRNG |

Полный заголовок включается в AAD каждой записи. Поэтому заголовок аутентифицируется каждой записью, а соль дополнительно влияет на производный ключ.

## 2. Запись

После заголовка идёт последовательность записей. Каждая запись имеет структуру:

| Относительное смещение | Размер | Поле |
|---:|---:|---|
| 0 | 4 | `plaintext_length`, uint32 big-endian |
| 4 | 1 | `flags` |
| 5 | N | ciphertext, длина равна `plaintext_length` |
| 5 + N | 16 | AES-GCM authentication tag |

Допустимые флаги:
- `0x00` — обычная запись;
- `0x01` — финальная запись (`FINAL`).

Каждая нефинальная запись должна содержать ровно 1 MiB открытых данных. Финальная запись содержит от 0 до 1 MiB включительно. Пустой файл представлен одной финальной записью с длиной `0` и тегом.

Максимум — 65 536 записей. Максимальный размер открытого файла — 64 GiB. Реализация отклоняет записи с неизвестными флагами, недопустимой длиной, отсутствующим финальным флагом и дополнительными байтами после финальной записи.

## 3. Производный ключ

На каждый контейнер вычисляется отдельный 32-байтовый ключ:

```text
file_key = HKDF-SHA-256(
    IKM  = master_key[32],
    salt = header.salt[16],
    info = ASCII("RCTS v0.1 AES-256-GCM container key"),
    L    = 32
)
```

## 4. Nonce

Для записи с индексом `i`, начиная с нуля:

```text
nonce(i) = header.nonce_prefix[4] || uint64_be(i)
```

Итоговая длина nonce — 12 байт (96 бит), как ожидает AES-GCM в этой реализации.

Индекс увеличивается на единицу после каждой записи. В пределах одного контейнера nonce не повторяется. Для разных контейнеров независимость производного ключа зависит от свежести случайной соли; случайный nonce-префикс добавляет разделитель nonce-пространства. Это вероятностная схема на базе CSPRNG, а не абсолютная гарантия отсутствия коллизий между всеми когда-либо созданными файлами.

## 5. AAD

Для каждой записи аутентифицируется следующая последовательность байтов:

```text
AAD(i) = header[33]
      || uint64_be(i)
      || uint32_be(plaintext_length)
      || flags[1]
```

Таким образом GCM tag связывает ciphertext с конкретным заголовком, порядковым номером, длиной и типом записи.

## 6. Завершение контейнера

Запись с `FINAL` завершает поток. После неё должен наступить EOF. Дополнительные байты запрещены. Удаление или перестановка записей нарушает структуру или проверку аутентификации.

## 7. Видимые метаданные

Формат v0.1 раскрывает:
- точный размер содержимого (с точностью до длины последней записи);
- число записей;
- фиксированный размер блока и версию формата.

Он не хранит исходное имя файла, путь и расширение. Сжатия и padding нет.

## 8. Совместимость

Значение `Version = 1` определяет формат RCTS v0.1. Любое несовместимое изменение структуры, семантики nonce/AAD, KDF или правил записей должно получить новую версию формата. Нельзя переиспользовать номер `1` для изменённого формата. Реализация 1.0 должна сохранять чтение v0.1 либо явно документировать отдельную миграционную утилиту и срок поддержки.
