# Security model and limitations

## Intended use

RCTS v0.1 is an experimental local file-encryption tool. Its intended goal is confidentiality and integrity of file contents when the master key is secret and the host environment is trustworthy. It is not production-reviewed and must not be the only protection for critical or irreplaceable data.+

## Assumptions

- The master key was generated with the project key generator and remains secret.
- The device, OS, user session, compiler/build chain and OpenSSL are not compromised.
- The filesystem behaves within the assumptions made by the implementation.
- The user maintains independent backups and can recover the key.

## Threats considered

An attacker may possess a container and its format/source and may modify, truncate, append or rearrange bytes. The format authenticates records and metadata; the parser rejects invalid structure. Knowledge of the format is not treated as a secret.

## Security properties intended by the design

- 256-bit master-key material generated by OpenSSL CSPRNG.
- Container-specific 256-bit key derived using HKDF-SHA-256 and a random salt.
- AES-256-GCM encryption with a 128-bit authentication tag per record.
- Per-container nonce prefix combined with a record index.
- Header and record metadata authenticated as AAD.
- Invalid key or tampered data causes authentication failure.
- Exclusive temporary-file creation and no-clobber publication.
- Bounded key-file reading and streaming file processing.

These are design properties, not proof that the implementation is bug-free.

## Out of scope

- Malware, a compromised operating system, malicious administrators, memory inspection, process injection or physical access.
- Key loss or unsafe user handling of the generated key file.
- Metadata privacy: filenames, paths, sizes, timing and the existence of a container are not hidden.
- Secure deletion of source files, key files, backups, temporary files or all memory copies.
- Availability against disk exhaustion, malicious filesystem behavior or denial of service.
- Defects in the application, compiler, dependency or cryptographic integration.

## Key handling

The key is not a password and has no password-strengthening step. Do not put it in source control, logs, command-line arguments, messages or untrusted cloud locations. Losing the key means losing access to encrypted data. Best-effort memory cleansing does not guarantee every copy is erased.

## File handling

RCTS aims to avoid replacing existing destinations and publishes completed output only after processing and finalization. Temporary files may remain after abnormal termination. Directory synchronization is best-effort; universal crash durability across filesystems is not claimed.

- Independent cryptographic review: **not completed**.

- Fuzzing and property-based testing: **planned/incomplete**.
- Production readiness or certification: **not claimed**.

## Vulnerability reporting

Report suspected vulnerabilities privately to the maintainer before publishing details. Include the affected revision, reproducible steps and environment. Do not attach keys or confidential plaintext.
